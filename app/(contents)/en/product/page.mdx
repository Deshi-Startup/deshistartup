# Product: Turn a Customer Task into Something Usable

> **In short:** Define the task a customer needs to complete, then test the smallest useful version of that experience. Building more features is not evidence that the task works.

## Choose what needs testing

| Uncertainty | Useful next step |
|---|---|
| Is this a real problem? | [Customer interviews](/en/validation/customer-interviews) |
| Will anyone take a meaningful next step? | [Test demand](/en/journeys/test-demand) |
| What could a first version look like? | [MVP examples](/en/validation/mvp-examples) |
| How should we define the experiment? | [MVP experiment planner](/en/validation/mvp-experiment-planner) |

A sketch, manual service or demonstration may answer a question before you build a full product. State honestly what works and what is simulated; do not promise capabilities you cannot deliver.

## Example: watch a customer complete one task

A **prototype** lets you demonstrate or test an experience before completing the product. **Usability** is whether the intended person can complete the task in the relevant conditions. Praise for the screen does not tell you whether the task works.

Imagine a fictional appointment tool for a Sylhet training centre. The task is “move a class and identify who needs to be informed.” A paper or clickable prototype with made-up names is enough for an initial usability check.

```text
User: administrator who changes timetables.
Start: a class is currently listed for Tuesday morning.
Task: move it to Wednesday and find which participants need notice.
Success: the new time and affected group are correctly identified without prompting.
Observation: the administrator changes the time but cannot find the affected group.
Interpretation: the relationship between a class change and notification is unclear.
Revision: show the affected group and a separate confirmation step beside the change.
Retest: another suitable administrator attempts the same task with dummy data.
```

Do not guide the person through the exact clicks while claiming the design worked unaided. Record where help was necessary. Also check the device, connection, language and accessibility conditions that actually matter for that group.

The first test is complete when you have an observed outcome and a reason for the revision. It does not prove that messages will be delivered reliably in a real system. Before using real contacts, payments or sensitive records, resolve the relevant data practices, consent, security and operating requirements.

## Write a one-task product brief

Describe **who / starting situation / task / successful outcome / likely failure / how you will observe it**. Add the device, connection, language and accessibility needs you must investigate with the intended users.

Ask someone from that group to try the task. Observe where they hesitate, need help or fail. Record what happened separately from your proposed solution. Fix the most important obstacle and try again.

Before handling real payments or sensitive information, identify the necessary permissions, data practices and safeguards. Start with the [legal roadmap](/en/legal-roadmap) for questions to resolve.
